## 提交信息格式
提交信息一般为以下的格式：
```
<类型>[作用域]: <描述>
[正文]
[脚注]
```
其中，`<类型>`和`<描述>`为必要内容，其他内容可省略。
`<描述>`请务必填写清楚，以方便查看您改动了什么。

提交信息的“结构符号”必须用**半角英文符号**。

我们并不强求您使用**英文**来说明除了`<类型>`以外的其他内容，当然如果您用了也无伤大雅


示例：
```
fix(登录系统): 修复人机验证无法通过的问题
```
```
refactor: 重写社区功能
```

Tips: 只有在发布新版本的时候可以选择不遵循提交规范，以发布`v2.0.1`版本为例：
```
v2.0.1
- 更新内容1
- 更新内容2
- 更新内容3
- ...
```
(`-更新内容x`可省略)

### `<类型>` 怎么填写

一般常见的扩展类型如下：

| 类型 | 含义 | 使用场景 | 示例 | SemVer 影响 |
| :--- | :--- | :--- | :--- | :--- |
| `docs` | 文档变更 | 仅修改文档，不涉及代码逻辑，如 README、注释、规范文档 | `docs(readme): 更新安装说明` | 通常不直接触发 |
| `style` | 代码格式 | 空格、缩进、分号、格式化等，不影响代码功能 | `style: 统一缩进为 2 空格` | 通常不直接触发 |
| `refactor` | 代码重构 | 既不新增功能，也不修复 Bug，仅调整代码结构 | `refactor(core): 拆分配置加载逻辑` | 通常不直接触发 |
| `perf` | 性能优化 | 提升性能、减少资源消耗、优化查询或渲染 | `perf(query): 减少重复数据库查询` | 通常不直接触发 |
| `test` | 测试变更 | 新增、修改或补充测试代码，不改变业务逻辑 | `test(auth): 补充登录失败用例` | 通常不直接触发 |
| `build` | 构建系统 | 构建脚本、打包配置、依赖版本、编译工具变更 | `build(deps): 升级 vite 到 5.0` | 通常不直接触发 |
| `ci` | CI 配置 | CI 配置文件、流水线脚本、自动化任务变更 | `ci: 增加 Node 20 测试矩阵` | 通常不直接触发 |
| `chore` | 杂项事务 | 不影响业务代码的杂项，如 `.gitignore`、锁文件、依赖维护 | `chore: 更新 .gitignore` | 通常不直接触发 |
| `revert` | 回滚提交 | 回滚之前的某次提交，建议在正文中说明回滚原因 | `revert: 回滚 "feat: 增加导出功能"` | 视回滚内容或团队约定 |

Tips:

- `docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore` 等扩展类型通常不直接触发语义化版本号变更。
- 如果扩展类型的提交中包含破坏性变更，仍应按破坏性变更处理，并触发 **MAJOR** 版本号递增。
- `revert` 类型建议在正文中说明被回滚的提交及回滚原因，必要时关联 Issue。
- 一次提交只做一件事，选择最能准确表达本次变更意图的类型。
- 不要用 `docs` 掩盖代码变更，也不要用 `chore` 掩盖功能或修复。
- 自定义类型必须在团队规范中明确列出，不建议随意新增。


扩展类型同样可以通过半角感叹号 `!` 或脚注 `BREAKING CHANGE:` 标记破坏性变更。

```text
refactor(config)!: 重命名配置文件
```

```text
perf(api): 调整缓存策略

BREAKING CHANGE: 缓存 Key 规则变更，旧缓存不再兼容。
```
